# ADR-001 · 안드로이드 래핑 방식

- 상태: **승인** — 2026-09-10 소유자 결정
- 작성일: 2026-09-10
- 관련: 실행 프롬프트 5.2 래핑 방식 비교, 7.2 WebView·브리지 보안

## 배경

`umsh.kr` 은 Express 가 `사주/` 아래 정적 HTML 을 직접 내려 주는 구조다. Next.js 같은
프레임워크 빌드 산출물이 없고, 라우팅을 서버가 소유한다.

측정한 사실이다.

| 항목 | 값 | 확인 방법 |
|---|---|---|
| 프런트 자산 총량 | 330.9MB (파일 800개) | `사주/` 전체 walk |
| HTML + JS + CSS | 8.2MB | 확장자별 집계 |
| 이미지 + 영상 + 폰트 | 322.7MB | png 108 / mp4 96 / webp 73 / ttf 40 |
| GET 라우트 | 117개 | `grep -c "^app.get(" src/server/app.ts` |
| 그중 리다이렉트 | 79개 | `grep -c "res.redirect"` |
| 파일 응답 | 32개 | `grep -c "res.sendFile"` |
| 정적 마운트 | 14개 | `grep -c "express.static"` |
| API 라우트 | 38개 | `/api/...` 경로 수집 |
| 유료 상담 | 19개 (검색 목록 노출 14개) | `catalog.ts` / `service-directory.ts` |

## 검토한 대안

### A. Capacitor + 웹 자산 번들

**성립하지 않는다.** 두 가지가 막는다.

1. **라우팅을 서버가 소유한다.** `/day/wedding` → `/day/wedding/01-step-1-story/index.html`
   같은 리다이렉트가 79개다. 번들하려면 이 79개를 앱 안에서 다시 구현해야 하고, 웹에서
   경로가 바뀔 때마다 앱을 다시 배포해야 한다.
2. **자산이 크다.** HTML/JS/CSS 만 골라도 8.2MB 라 번들 자체는 가능하지만, 그 화면들이
   참조하는 이미지·영상 322MB 는 결국 네트워크에서 받아야 한다. 오프라인 이득이 크지 않다.

콘텐츠를 자주 배포하는 현재 운영 방식과도 맞지 않는다. 상담 문구 한 줄을 고칠 때마다
앱 심사를 기다리게 된다.

### B. Capacitor + `server.url` (현재 구현된 방식)

`https://umsh.kr` 을 그대로 띄운다. Capacitor 가 원격 페이지에 브리지를 주입하므로
스플래시·상태바·딥링크·결제 플러그인이 동작한다.

**실행 프롬프트 5.2 가 이 방식을 지적한다.** Capacitor 공식 설정 문서는 `server.url` 을
개발용 live reload 목적이라고 명시하고 운영용으로 의도하지 않았다고 적는다.

그 지적에서 실제로 걸리는 것은 두 가지다.

1. **번들 자산이 없어 순수 원격 래퍼가 된다.** 실행 프롬프트 5.3 과 R02(제한된 기능)
   위험에 그대로 걸린다. 첫 실행에 네트워크가 없으면 크롬 오류 화면이 나온다.
2. **원격 origin 이 브리지 전체를 갖는다.** `umsh.kr` 이 내려 주는 JS 가 결제 플러그인까지
   부를 수 있다. 우리가 그 도메인을 소유하므로 통제 범위 안이지만, 웹 배포가 오염되면
   앱 권한까지 함께 오염된다. 7.2 의 "원격 웹 변경으로 앱 권한·구매를 몰래 바꾸는 설계
   금지" 와 맞닿는다.

### C. Kotlin + 관리형 WebView

WebView 를 직접 만들고 브리지에 필요한 메서드만 노출한다. 원격 URL 을 띄우는 것이 이
방식의 정상 사용법이라 B 의 첫 번째 지적에서 자유롭다. 노출 면적도 우리가 정한다.

비용은 실물이다. 결제(Play Billing), App Links, 파일 다운로드·공유, 뒤로 가기, 세션 복구,
오류·오프라인 화면을 전부 직접 짜야 한다. 지금 Capacitor 플러그인이 대신하는 부분이다.

### D. TWA + PWA

`사주/` 에 manifest 도 service worker 도 없다(확인함). PWA 요건부터 새로 만들어야 하고,
Play 결제를 붙이기도 가장 불리하다. 제외한다.

## 검토 결과

**B 를 유지하되 B 의 두 지적을 실제로 해소한다.**

해소 방안:

1. **로컬 셸을 붙인다.** `server.errorPath` 로 `app-shell/www/index.html` 을 연결했다.
   로드가 실패하면 크롬 오류 화면 대신 브랜드 안내 화면이 뜨고, 첫 실행이 네트워크
   없이도 설명되는 화면에서 멈춘다. Capacitor 가 지원하는 설정이라 네이티브 코드를
   따로 짜지 않았다. 이 화면은 플러그인에 접근하지 못하므로 안내와 다시 시도만 한다.
   (TASK B06)
2. **브리지 노출 범위를 문서화하고 고정한다.** `allowNavigation` 은 이미 `umsh.kr` 만
   허용한다. 여기에 없는 주소는 시스템 브라우저로 나가고 브리지를 상속하지 않는다.
   결제 권한은 서버가 구글 영수증으로 다시 검증하므로, 웹 JS 가 결제 플러그인을 불러도
   서버 검증 없이 열람 권한이 생기지 않는다. (이미 구현·테스트됨)

## 결정

**B 를 채택한다.** 2026-09-10 소유자 판단: "기존 서비스 유지고 웹을 앱으로 감싸서
그대로 서비스하는 방식".

이 결정이 뜻하는 것.

- 웹 서비스는 앱을 위해 구조를 바꾸지 않는다. 앱은 배포된 `umsh.kr` 을 그대로 띄운다.
- 콘텐츠·문구·화면 수정은 지금처럼 웹 배포만으로 반영된다. 앱 재배포가 필요 없다.
- 웹에 손대는 것은 앱 때문에 반드시 필요한 경우로 한정한다. 현재 그런 항목은 결제 분기
  (`app-billing.js` 로드 한 줄)와 App Links 검증 파일 두 가지뿐이다.

C(Kotlin+관리형 WebView)로 가지 않는다. 다만 아래 두 가지는 B 의 조건으로 남는다.

| 조건 | 상태 |
|---|---|
| 로컬 오류 화면 연결 | **완료** — `server.errorPath: index.html`. 설정이 네이티브 프로젝트에 반영된 것과 화면 렌더링을 확인했다. 실기기에서 오류를 실제로 유발한 확인은 아직 없다 |
| 브리지 노출 범위 고정 | **완료** — `allowNavigation` 은 `umsh.kr` 만. 그 밖의 주소는 시스템 브라우저로 나가며 브리지를 상속하지 않는다 |

심사에서 `server.url` 자체가 문제로 지적되면 그때 C 전환을 다시 검토한다. 전환하더라도
서버 구현(`/api/payment/google/verify`, 영수증 검증, 멱등성)은 그대로 재사용된다.

## 되돌리는 방법

`android/` 폴더를 통째로 제거하면 웹 서비스는 변경 전 상태로 돌아간다. 서버에 추가한 것은
`/.well-known/assetlinks.json` 라우트와 `/api/payment/google/*` 두 갈래뿐이고, 둘 다 기존
웹 흐름을 건드리지 않는다(회귀 테스트 381개 통과로 확인).
