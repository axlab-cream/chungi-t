# 운명상회 KG이니시스 결제창 실행 복구

## 증상

- 운영 결제 페이지에서 주문 저장 실패가 먼저 발생했다.
- 스키마를 보완한 뒤에는 KG이니시스가 Verification 오류로 결제 UI 진입을 거부했다.

## 원인

1. 서버 주문 insert 계약에는 `revision`이 포함됐지만 운영 주문 테이블에는 컬럼이 없었다.
2. PC 요청·승인 signature/verification의 SHA-256 입력을 값만 연결해 만들었다. KG이니시스 표준결제는 필드 순서가 고정된 NVP `key=value&...` 문자열을 요구한다.
3. 같은 시점의 Node `url.parse()` deprecation 경고는 결제 실패의 직접 원인이 아니었다.

## 수정

- `revision integer not null default 0`과 비음수 제약을 migration으로 운영 DB에 적용했다.
- 요청 서명은 `oid`, `price`, `timestamp`, 검증값은 여기에 `signKey`를 더한 공식 NVP 순서로 생성한다.
- 승인 및 PC 망취소 보조 서명도 `authToken`, `timestamp`, 검증값의 `signKey`를 공식 NVP 순서로 생성한다.
- 정확한 SHA-256 입력 문자열을 회귀 테스트로 고정했다.

## 검증

- 결제 집중 테스트 15/15, 전체 저장소 962/962, TypeScript와 Vercel build 통과.
- 운영 배포 후 신규 주문은 승인 전 `ready`, `revision=0`으로 저장됐다.
- KG이니시스 실제 결제 UI에서 결제수단, 카드사, 상품명과 금액 표시를 확인했다.
- 카드 인증·승인·과금은 실행하지 않았다.

## 결제창 닫기 복귀

- PC 표준결제의 닫기 URL은 결제 iframe 안에서 열린다. 닫기 문서가 자기 창에만 `window.close()`를 호출하면 빈 안내 문서가 iframe에 남는다.
- 닫기 문서가 동일 출처 부모 또는 opener로 명시적 이벤트를 보내고, 부모 결제 화면이 그 이벤트를 받아 복귀해야 한다.
- 복귀 경로는 결제 진입 시 전달된 내부 `returnTo`를 우선하고, 없으면 상품의 서버 카탈로그 기본 경로를 사용한다. 다른 origin은 거부한다.
- 운영 실제 닫기 버튼과 취소 확인을 눌러 상품 시작 페이지 복귀를 검증했다. 승인·과금은 실행하지 않았다.

## 재사용 규칙

- 런타임 insert 타입이 바뀌면 동일 배포 전에 운영 스키마 migration과 실제 컬럼 재조회를 함께 수행한다.
- PG 해시는 값 연결로 추측하지 말고 공급사 문서의 필드명·순서·구분자를 exact-hash 테스트로 고정한다.
- PG UI 진입 성공과 실결제 성공은 별도 게이트로 기록한다.
- PG가 제공하는 iframe 닫기 URL은 부모 화면의 복귀 이벤트와 함께 통합 테스트한다.

비밀키, 사용자 정보, 주문번호, 결제 응답 전문은 이 문서에 저장하지 않는다.
