# 운명상회 카피·결제 UX 품질 점검

## 목표

10~20대 사용자가 첫 화면에서 `무엇을 고를 수 있는지`, `얼마인지`, `누르면 어디로 가는지`를 3초 안에 이해하고, 로그인·결제 뒤 입력하던 서비스로 끊김 없이 돌아오도록 한다.

## 카피 점검 결과

| 위치 | 기존 문제 | 반영한 문구/원칙 |
| --- | --- | --- |
| 메인 히어로 | 감성은 있으나 어떤 상품을 고르는 화면인지 늦게 인지됨 | `지금, 제일 궁금한 운명부터` / `연애 · 돈 · 일 · 집까지, 오늘의 고민에 맞는 풀이를 골라보세요.` |
| 대표 상품 CTA | `보기`, `이 운명 확인하기`가 상품 탐색과 결제를 함께 암시함 | `이 풀이 보기`로 통일. 상세 화면의 결제 CTA는 `이니시스 결제창 열기`로 분리 |
| 무료 티켓 | 무료 진입점이 회원가입 안내보다 약함 | `오늘 흐름, 무료로 먼저 보기` / `무료로 확인하기` |
| 추천 섹션 | 인기 기준이 모호함 | `요즘 가장 많이 고른 풀이` |
| 하단 메뉴 | 보관함·MY의 역할이 추상적임 | 풀이, 결제 내역, 사주 프로필을 설명하고 로그인 후 원래 화면으로 복귀 |

### 카피라이터 관점

- 후킹은 운명 일반론보다 사용자의 즉시 고민을 앞에 둔다. `나, 회사 옮겨도 될까?`, `나는 왜 돈이 안 모일까?`, `지금 사는 집, 나랑 맞을까?`처럼 질문형 상품명은 유지한다.
- 과장된 확정 표현 대신 `흐름`, `기준`, `확인`을 사용해 신뢰를 지킨다.
- 전문 용어는 상품 설명의 보조 정보로 내리고, 제목은 일상어로 먼저 제시한다.

### UX 라이팅 관점

- 모든 유료 CTA는 상품명과 금액이 같은 화면에 보인다.
- 이미지 배너 영역은 이미지가 주 정보를 담당하고, 접근성용 `aria-label`에만 상품명·가격·행동을 남긴다.
- 결제 동작은 `결제창 열기`, 성공 후 동작은 `풀이 이어서 입력하기`로 구분한다.
- 하단 메뉴의 잠금 상태는 `로그인 필요`와 `사주등록 필요`를 다르게 보여준다.

## 결제 프로세스

### 구현된 공통 흐름

`서비스 선택 → 공통 로그인 → 사주 프로필 확인 → 주문 생성(서버 금액 확정) → 이니시스 표준결제창 → 서버 승인 → 결제 결과 → 원래 서비스 복귀 → 입력값 자동 복원 → 풀이 열람`

### 보강한 페이지

- `/payment`: 상품·금액·이메일·휴대폰·약관 동의와 이니시스 결제창 진입
- `/payment/result`: 성공·취소·실패 결과 및 원래 서비스 복귀
- `/payment/close`: 결제창 닫기 콜백
- `/orders`: 공통 계정 결제 내역
- `/leave`: 회원 탈퇴와 결제 기록 법정 보관 안내

상품 금액은 `src/payment/catalog.ts`에서 관리하고, 주문 생성 시 서버가 다시 확정한다. 결제 후 서비스별 입력값은 세션 스토리지에 30분 동안 보관하고, 승인된 주문에 한해 자동 복원한다.

## 이니시스 가이드 대조

첨부된 `PayMtd_GUIDE_풍수아씨_완성.pptx`의 일회성 상품, 카드·휴대폰 결제, 공통 약관·환불·탈퇴 화면 요구를 기준으로 반영했다. 현재 코드는 KG 이니시스 Standard Pay의 `INIStdPay.js`와 서버 승인 구조를 사용한다.

운영 전 필수 설정:

1. Vercel Production에 `INICIS_MID`, `INICIS_SIGNKEY`, `PUBLIC_BASE_URL=https://umsh.kr` 설정
2. 주문 저장소에 `DATABASE_URL` 또는 `SUPABASE_SERVICE_ROLE_KEY`와 `supabase-payment-orders.sql` 적용
3. 이니시스에 `https://umsh.kr/api/payment/inicis/return` 승인 콜백과 `https://umsh.kr/payment/close` 닫기 URL 등록
4. 테스트 MID로 카드 승인·취소·실패·창 닫기·중복 콜백을 검증한 뒤 운영 MID로 전환

SignKey는 브라우저에 전달하지 않는다. 카드번호도 운명상회 서버에 저장하지 않고 이니시스 결제창에서 처리한다. 휴대폰 결제 노출 여부는 실제 이니시스 계약 및 MID에 활성화된 결제수단을 확인한 뒤 운영한다.

## 잔여 리스크

- 현재 운영 환경에 이니시스 MID/SignKey와 영속 주문 저장소가 설정되지 않으면 결제 화면은 의도적으로 `결제 모듈 연결 전` 상태로 보인다. 이는 가짜 결제를 막기 위한 운영 차단이다.
- 로컬 결제창 검증은 `PAYMENT_TEST_MODE=true`로만 켤 수 있으며 `NODE_ENV=production`에서는 강제 비활성화된다. 특정 이메일을 기준으로 결제를 우회하지 않는다.
- 이니시스 실제 승인·취소는 가맹점 계약과 테스트 계정이 필요하므로 코드만으로 실결제 성공을 가장할 수 없다.
- 자동 롤링은 사용자가 마우스를 올리거나 포인터를 드래그하는 동안 멈추며, 일반 클릭은 네이티브 앵커 이동을 사용한다. `prefers-reduced-motion` 사용자는 자동 롤링을 보지 않는다.

## 검증 기준

- `npm run typecheck`
- `npm test -- --runInBand`
- `npm run vercel-build`
- PC 클릭으로 `/place/home` 진입
- 대표 상품 페이지 표시가 `1/3`~`3/3`으로 갱신되고 자동 롤링
- 결제 후 원래 서비스 입력 복원 및 `/api/payment/orders/:orderId/viewed` 처리
