## Improvement — 콘텐츠와 화면

17개 유료 보고서의 항목별 초안은 총 608개다. 관계 계열 7종 321개, 직업·금전·생활 계열 6종 223개, 종합·주거·이직·시험 4종 64개를 각 항목의 질문과 판단 기준에 맞춰 분리했다. 오늘의 운세는 날짜별 저장 결과로 별도 처리한다.

초안은 유료 완성본이 아니다. 관계 계열 초안은 대체로 585~761자이고, 연락 거부처럼 안전을 우선하는 분기는 일부 문장이 반복된다. 실제 유료 본문은 저장된 항목을 바탕으로 생성·검수한 뒤에만 완료 상태가 된다.

- 공통 목표: 현재 확인된 상태 → 전통적 해석의 근거와 한계 → 쉬운 현실 장면 → 유지하거나 조정할 선택을 자연스럽게 연결한다. 문제가 없으면 유지할 조건을 설명한다.
- 문체: 첫 전문용어와 한자를 풀어 설명하고, 짧은 의미 문단을 사용한다. 한자 치환 때문에 설명이 중첩되거나 문장 어미가 손상되는 후처리도 수정했다.
- 분량: 프롬프트는 항목당 1,800~2,600자, 6~9문단을 목표로 한다. 승인 하한은 1,000자·5문단이며, 목표 분량은 강제 상한/하한이 아니다. 길다고 의미 품질이 보장되지는 않는다.
- 생시 미상: 시간 기둥·강약·용신·정밀 시기와 관련된 확정 설명을 제한한다. 알려지지 않은 시간은 결과 ID에도 반영한다.
- 티저: 두려움을 키우거나 확정적 미래를 약속하지 않는다. 입력에서 확인 가능한 해석과 유료 본문에서 더 볼 판단 기준을 구분한다.
- 화면: 검정·금색 브랜드 톤, 전체 문단 출력, 항목 접기/펼치기, 구매 내역·고유 주소 이동을 공통으로 제공한다. 고정된 가짜 점수·미래 날짜·상대 외모/직업 샘플을 실제 결과처럼 보여 주는 경로를 제거했다.

의미 품질은 자동 검사만으로 입증할 수 없다. 검수기는 문장·구조상의 알려진 위험을 탐지하며, 명리 해석의 과학적 예측력을 검증하거나 전환율 상승을 증명하지 않는다.

## Theory / 재사용 가능한 저장 패턴

`입력과 UUID 저장 → 생성 임대 획득 → 시도 ID 저장 → 모델 원문·사용량 저장 → 검수 → 조건부 완료 저장 → ID로 읽기`

- 보고서 `resultId`, 항목 `generationId`, 각 모델 시도 ID를 생성한다. 외부 주소는 `/r/<resultId>`다.
- 동일 입력의 기존 canonical ID는 호환한다. 구형 완료 기록에 새 필드가 없어도 기존 주소와 본문을 유지하고 안정된 항목 ID를 계산한다.
- 같은 결과를 다시 열 때 모델을 호출하지 않는다. 실패 항목은 명시적 재시도만 허용하며, 이미 완료된 항목은 `retry=true`여도 다시 생성하지 않는다.
- 새 입력·맥락은 별도 결과로 다룬다. 기존 결과의 ID·소유자·입력·완료 본문은 갱신 API로 덮어쓸 수 없다.
- UUID는 접근 권한이 아니다. 로그인 소유자와 구매 권한을 서버에서 검사한다. 상담은 저장된 부모 보고서와 결제 취소 상태도 확인한다.
- Supabase/Postgres는 기존 JSON payload에 revision 등을 저장한다. 운영 스키마를 직접 변경하지 않았다. 로컬 파일 저장은 개발 전용이며 운영에서는 영구 DB가 없으면 생성을 거절한다.
- 파일 저장은 원자적 교체와 잠금을 사용한다. 오래된 잠금은 자동 삭제하지 않고 실패 처리한다. 복구 시 해당 단일 결과의 잠금과 실행 중인 프로세스를 확인해야 한다.
- 원문·시도 이력·토큰 사용량은 내부 기록이며 클라이언트 결과에서 제거한다. 인증 토큰은 저장하지 않는다.
- 오늘의 운세는 소유자·프로필·한국 날짜별 결과를 저장하므로 어제 결과 ID를 열어도 오늘 내용으로 바뀌지 않는다.
- 상담도 요청 ID를 통한 중복 방지와 영구 저장을 적용한다. 상담 답변을 보존하기 위해 로그인된 사용자 경로로 연결했다.
- 응답 후 방치되는 일괄 생성을 제거했다. 독자는 최대 두 항목을 병렬 요청하며 서버는 항목 HTTP 요청 안에서 생성을 기다린다. 배포 설정의 함수 최대 실행 시간은 300초다.

## 운영 반영 전 확인할 조건

1. 현재 연결된 운영 Supabase에 실제 로그인 사용자로 저장·조회·RLS·구매 권한을 종단 검증해야 한다. 이번에는 운영 사용자 토큰/관리자 자격으로 DB를 변경하지 않았다. 익명 조회 거절만 확인했으며, 이것이 인증 사용자 전체 흐름의 통과를 뜻하지 않는다.
2. 배포 후 함수 실행 시간과 모델 지연, 한 상품 전체 생성 비용, 다수 사용자의 동시 생성을 관찰해야 한다. 이번 실생성은 608개 전수가 아닌 대표 6개 항목이다.
3. 이미 완료된 고객 본문은 보강 규칙으로 자동 덮어쓰지 않는다. 새 생성에 새 규칙이 적용되며 기존 결과는 그대로 재조회한다.
4. 기존의 보고서 ID 미연결 구매 호환 규칙은 유지했다. 구매 정책 변경은 이번 작업 범위에 포함하지 않는다.
5. 전환율 개선은 아직 실험하지 않았다. 추후 티저 이탈률·구매율과 내용 불만을 함께 측정해야 한다.
