# 코퍼스 개정 시 캐시 무효화 정책

최종 갱신: 2026-09-14 · 적용 커밋: `feat: 코퍼스 캐시 세대(cacheEpoch) 도입`

---

## 한 줄 요약

**저장된 해석을 버릴지 말지는 `data/tone-v2/corpus/registry.json` 의 `cacheEpoch` 하나가 결정한다.**
코퍼스 파일을 고쳐도 이 값을 그대로 두면 재생성은 한 건도 일어나지 않는다.

---

## 도입 전에 실제로 무슨 일이 있었나

`createReportId()` 는 `getCorpusSnapshot().fingerprint` 를 키에 넣고 있었고,
그 지문은 **서비스별이 아니라 활성 팩 28개 전부의 내용 해시**를 한 덩어리로 묶은 값이었다.

동일한 계산 구조로 재현한 결과 — 어느 팩 하나만 건드려도 전역 지문이 통째로 바뀐다:

```
기준                              c1dc26209131b7bb5e7c01c62e74
love-this-year 1글자 수정         1674c7d136c25fdd83e07bd8ba77   전체 변경
wedding-day    1글자 수정         b5d19d308de2badaf005e20d321c   전체 변경
consultation-templates 1글자 수정 ecee69e709fcda97b73c144c3d0b   전체 변경
```

그런데 경로마다 결과가 정반대였다.

| 경로 | 리포트 ID 구성 | 코퍼스 개정 시 |
|---|---|---|
| `/api/saju/analyze` (cmdg 종합) | 생년월일 + 맥락 + **전역 코퍼스 지문** + 소유자 | 전량 재생성 + **결제 권한 상실** |
| 특화 서비스 15개 | 소유자 + 생년월일 + 입력 + 서비스키 (코퍼스 미참조) | **영원히 갱신 안 됨** |
| 오늘운 daily | 고정 키 `daily-reading-v3` | 사람이 키를 바꿀 때만 |

결제 권한이 끊기는 구조는 이랬다. 주문은 결제 시점의 리포트 ID 에 묶인다.

```ts
function orderUnlocks(order, owner, productKey, reportId) {
  if (!order.reportId || !reportId) return true
  return order.reportId === reportId   // 지문이 바뀌면 여기서 false
}
```

지문이 바뀌면 `findUnlockingOrder` 의 마지막 폴백(`unlocking[0]`)까지 빈 배열이 되어,
**이미 결제한 사용자가 결제 화면으로 되돌아간다.**

## 새 구조

### 1) 캐시 세대 — `cacheEpoch`

```json
{
  "version": "tone-v2.2.0.20",
  "cacheEpoch": "",
  ...
}
```

- **빈 문자열 = 도입 시점 그대로.** 이 값이 비어 있으면 리포트 ID 계산에서 항목 자체가 빠지므로
  배포해도 기존 리포트 ID 가 한 건도 바뀌지 않는다.
- 다음 값은 `"e2"`, 그다음 `"e3"` 처럼 **단조 증가**시킨다. 되돌리면 과거 해석이 되살아난다.
- 코퍼스 내용 해시(`fingerprint`)는 감사용으로 계속 기록하되 **캐시 키로는 쓰지 않는다.**

### 2) 계보 키 — `lineageId`

생년월일·맥락·소유자·세대만 보는 키. 코퍼스 내용에 의존하지 않는다.

- **캐시 승계**: 리포트 ID 가 바뀌어도 같은 계보의 기존 해석을 그대로 이어 쓴다 → LLM 재호출 0건
- **결제 승계**: 세대를 올려 ID 가 바뀌어도 지난 ID 에 묶인 주문을 되짚어 찾는다
- 레코드에 저장된다. 특화 서비스의 계보 키는 역산이 불가능하므로 저장이 필수다

### 3) 특화 서비스에도 세대 적용 — `withCorpusEpoch()`

서비스별 ID 생성기(`createMoneySaveReportId` 등)는 코퍼스를 전혀 보지 않는다.
그 위에 한 겹 씌워, **세대를 올렸을 때만** ID 가 바뀌게 했다.
기준 세대에서는 항등함수이므로 기존 저장분이 그대로 열린다.

## 운영 판단 기준

| 개정 내용 | 세대 | 결과 |
|---|---|---|
| 오타 수정, 문장 다듬기, 주석 | 그대로 | 재생성 0건. 새 해석부터 반영 |
| 예시·표현 추가 (기존 판단 불변) | 그대로 | 위와 같음 |
| 근거 규칙 변경, 섹션 구성 변경 | **상향** | 전 서비스 재생성. 결제 권한은 계보로 승계 |
| 잘못된 해석을 낳은 오류 수정 | **상향** | 위와 같음 |
| 서비스 페르소나 전면 개편 | **상향** | 위와 같음 |

### 세대를 올릴 때 확인할 것

1. 재생성 규모 — `select count(*) from cheongi_reports where payload->>'status' = 'complete'`
2. LLM 비용 — 위 건수 × 서비스당 섹션 수
3. 사용자 고지 — 이미 읽은 해석의 문장이 바뀐다. 결제한 사람에게는 설명이 필요하다
4. 배포 후 첫 열람은 느리다. 재생성이 끝날 때까지 6-1 진행률이 돈다

### 올리는 방법

```jsonc
// data/tone-v2/corpus/registry.json
"cacheEpoch": "e2",
```

한 줄. 배포하면 그때부터 새 ID 로 생성된다. 기존 레코드는 삭제하지 않는다 —
`저장된 해석` 목록에는 계속 남고, 결제 권한도 계보로 이어진다.

## 회귀 방지

`tests/unit/corpus-cache-epoch.test.ts` — 8 tests, 뮤테이션 9/9 감지.

| # | 고정하는 계약 |
|---|---|
| 1 | 기준 세대에서 리포트 ID 가 도입 이전 공식과 **완전히 같다** / 세대를 올리면 반드시 바뀐다 |
| 2 | `withCorpusEpoch` 는 기준 세대에서 항등, 세대 상향 시 변경 |
| 3 | 실제 코퍼스 파일을 고쳐도 계보 키는 불변 (지문은 바뀜을 같이 확인) |
| 4 | 세대를 올리면 계보 키도 함께 바뀐다 |
| 5 | 코퍼스가 바뀌어도 같은 계보의 해석을 이어 쓴다 / 세대가 다르면 새로 만든다 |
| 6 | 계보 키 없는 경로는 기존 동작(정확 일치)을 유지 |
| 7 | 특화 서비스 15개가 전부 `epochScopedIds` 와 계보 키를 통과시킨다 |
| 8 | 역산 불가능한 계보 키도 레코드에 기록되고 조회된다 |

7번이 **새 서비스를 추가하며 계보 키를 빠뜨리는 실수**를 막는다.

## 남은 것

- 저장된 상담 기록(`saved-chat`)은 계보 승계 대상에서 제외했다. 상담은 해석과 수명이 다르다.
- 익명(비로그인) 레코드는 목록 조회 대상이 아니라 계보 승계가 적용되지 않는다.
  결제가 없는 경로이므로 실익이 없다.
- `daily-reading-v3` 는 고정 키를 그대로 뒀다. 오늘운은 날짜별이라 세대와 무관하다.
