# 비회원(익명 계정) 도입 계획 — 로그인·가입 화면을 고치기 전에 읽기

- 작성: 2026-10-14, 기획 결정은 대표(kimym7605)와 Claude 세션에서 합의
- 상태(2026-10-14): 1~4단계 구현. #120·#145·#146 머지, 3단계(이어받기) PR 진행. 운영 스위치 `GUEST_SIGNIN_ENABLED` + Supabase 익명 로그인을 켜야 동작
- 관련: PR #122(천명사주 가입 전 티저, `invisible-creator`), PR #120(서버 회원 전용 분리)

로그인, 가입, 결제 유도, 천명사주 티저, `/api/saju/analyze`, `/api/play/*`, `umsh-auth-session.js`,
`umsh-funnel-auth-gate.js` 를 고치는 사람(사람이든 AI든)은 이 문서를 먼저 읽는다.
이 계획과 다르게 바꿔야 하면 PR 설명에 이유를 적고 대표에게 알린다.

## 1. 왜 하나

로그인 벽에서 이탈이 난다. 다른 서비스처럼 무료로 보는 데까지는 로그인 없이 보여 주고,
저장·결제·대화처럼 "더 가져가는" 순간에만 SNS 로그인을 받는다. 동시에 **비회원 수를 셀 수 있어야 한다.**

- 비회원 = 사주 정보를 입력했지만 SNS(카카오·네이버·구글) 로그인은 안 한 사람
- 방식 = Supabase 익명 로그인(`signInAnonymously`). 서버가 알아보는 임시 계정 id 를 갖는다.

## 2. #122 와 이 계획의 차이

| | #122 (머지됨, 운영 반영) | 이 계획 |
|---|---|---|
| 적용 범위 | 천명사주만 | 천명사주 + 서비스 14개 + 오늘 운세 + 서브 콘텐츠 |
| 비회원 식별 | 없음. `guestTeaser: true` 로 계산값만 받고 아무것도 저장 안 함 | 익명 계정 id. 프로필에 `profile_payload.account_type = 'guest'` 표시 |
| 비회원 수 집계 | 안 됨 | 관리자에서 비회원 수·전환율 |
| 로그인 시점(천명사주) | 티저 → "운명 거래하기"·"결제하기"에서 로그인 | **#122 흐름 그대로 유지** |
| 로그인 후 | 같은 입력으로 다시 분석 | 비회원 결과·사주 정보를 회원 계정으로 옮김(다시 입력 안 함) |

결론: **#122 화면 흐름은 살리고, 그 밑에 익명 계정과 비회원 집계를 붙인다.** #122 를 되돌리지 않는다.

## 3. 익명 로그인을 켜면 깨지는 가정 — 꼭 확인

익명 계정도 `session.access_token` 을 가진다. **"토큰이 있으면 회원"이라는 가정은 운영에서 익명 로그인을 켜는 순간 틀린다.**

- 천명사주 `startCheckout`(`사주/사주/index.html`)의 `!session?.access_token || state.guestPreview` 검사 → 익명 계정이면 `is_anonymous` 로 회원 여부를 봐야 한다.
- `bindServiceSession`, play 테스트 `app.js`, `umsh-report-access.js` 등 토큰만 보는 곳 전부 같은 문제.
- 회원 여부는 Supabase 세션의 `user.is_anonymous === true` 로 판단한다. 서버는 PR #120 의 `requireMemberUser`(401 `MEMBER_REQUIRED`)가 막는다.
- 천명사주 비회원이 익명 계정을 갖게 되면 `/api/saju/analyze` 는 `guestTeaser` 분기가 아니라 일반 분석 경로를 탄다. 2단계에서 맞춘다.

## 4. 로그인 받는 곳 (합의안)

| 화면 | 비회원 | 로그인 |
|---|---|---|
| 홈, 사주 입력(천명사주·서비스 14개·오늘 운세) | 가능 | 없음 |
| 천명사주 티저 | 봄 | "운명 거래하기"·"결제하기" (#122 화면) |
| 서비스 무료 미리보기 | 봄 | 다 읽으면 권유 바텀시트(닫기 가능) |
| 서브 콘텐츠(연애 본능·금사빠) 결과 | 결과까지 봄 | 결과 화면에서 "저장하려면 로그인" 권유 바텀시트 |
| 잠긴 유료 장, 결제, 쿠폰 | 불가 | 필수 바텀시트 |
| 결과 채팅, 1:1 상담, 마이페이지 회원 메뉴 | 불가 | 필수 바텀시트 |

- 권유 시트는 결과 하나에 한 번. 닫으면 결과 맨 아래에 "로그인하고 저장하기" 한 줄만 남긴다.
- 필수 시트에는 "지금 본 결과는 그대로 이어져요"를 넣는다.
- 확정 대기: 천명사주 안 연애운의 비회원 허용, 운명록·보관함 비회원 공개.

## 5. 공용 기기(PC방) 보호

- 비회원 세션은 `sessionStorage` 에 두고, 1시간 쓰지 않으면 지운다(대표 결정).
- 비회원의 생년월일을 `localStorage` 에 남기지 않는다(지금 `cheongi_user_birth_profile_v1` 에 남는 것도 정리).
- "기록 지우고 나가기" 버튼은 넣지 않는다(대표 결정).
- 로그인할 때 비회원 결과를 옮기기 전에 "방금 본 결과 N개를 저장할까요?"로 묻는다(이름·생일은 띄우지 않음).

## 7. 약관 동의·비회원 관리 (2026-10-15 대표 결정)

- **무료 결과 바텀시트 = 동의 + SNS 로그인.** 필수: 이용약관, 개인정보 수집·이용, 만 14세 이상. 선택: 마케팅 수신. 필수를 안 누르고 SNS 버튼을 누르면 빠진 항목이 흔들린다(따로 팝업 없음). 로그인 화면(`/signup#login`)에도 같은 묶음을 둔다. 기존 회원은 다음 로그인 때 한 번 다시 받는다. 화면은 PR #172.
- **동의 기록** `umsh_consents`: 고치지 않고 쌓기만 한다. 버전은 `CONSENT_VERSION`(src/user/guest-ledger.ts). 약관을 고치면 버전을 올린다.
- **비회원 = 같은 기기 + 같은 사주.** 기기는 브라우저 `localStorage` 의 무작위 기기 번호(`umsh_device_id_v1`). 다른 기기면 이름·생일이 같아도 다른 사람. SNS 로그인하면 그때 회원에 잇는다. 장부 `umsh_guest_people` 한 줄 = 한 사람, 방문(익명 계정)마다 방문 수 +1.
- **어드민:** 회원 관리는 SNS 회원만, 회원 › 비회원 관리 새 메뉴(필터: 전체·전환 안 함·회원 전환·30일 지남). 회원 상세에 동의 이력·비회원 시절 기록. 서버는 PR #173.
- **30일 정리(수동):** 마지막 방문 30일이 지나면 대시보드 처리 필요에 "정리 대기 비회원"이 뜬다. 정리하면 이름·생일(월·일)·시를 지우고 방문 계정·결과를 지운다. 출생 연도·성별·서비스·방문 수·날짜는 통계로 남긴다. 처리방침도 이 기준으로 고쳤다.
- **운영 적용:** `supabase/migrations/20261015120000_guest_people_and_consents.sql` 을 Supabase SQL Editor 에서 실행해야 기록이 쌓인다. 실행 전에는 화면·로그인은 그대로 되고 기록만 빠진다.
