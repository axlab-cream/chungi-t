# 권한 및 민감정보 설계
현재 admin.ts는 유료 리포트 열람 예외이며 운영 관리자 권한이 아니다.

## 역할 행렬
R=조회, W=변경, A=승인, -=불가. 민감 원문은 별도 권한이다.

| 영역 | 운영총괄 | 콘텐츠 | 지식검수 | CS | 재무 | 엔지니어 | 분석가 |
|---|---|---|---|---|---|---|---|
| 운영 대시보드 | R | R(범위) | R(품질) | R(지원) | R(금융) | R | R(집계) |
| 콘텐츠·미디어 | A | W | R | R | - | R | - |
| 코퍼스·프롬프트 | A | R | W/A* | - | - | W | R(메타) |
| 주문 | R | - | - | R(마스킹) | R | R(메타) | R(집계) |
| 환불 | A | - | - | 요청 | 요청/A* | - | - |
| 회원 | R(마스킹) | - | - | R(마스킹) | R(필요필드) | R(메타) | - |
| 실패 리포트 재시도 | W | - | - | 요청 | - | W | - |
| 직원 권한 | W | - | - | - | - | - | - |
| 로그·감사 | R | R(자신 변경) | R(지식 변경) | R(문의) | R(금융) | R(운영) | R(집계) |

*본인 작성/요청한 변경은 본인이 승인할 수 없다. 작은 팀은 다른 승인자를 지정한다. 역할은 합성 가능하나 작성자-승인자 분리 조건을 우회하지 못한다.

## 인증·세션
기존 인증 provider를 재사용하되 직원 membership은 서버 관리 데이터로 검증한다. 사용자 편집 가능한 profile/user_metadata를 역할 원천으로 사용하지 않는다. 권한 회수는 다음 요청에서 서버 membership 상태로 반영한다.
쿠키 방식 선택 시 HttpOnly/Secure/SameSite와 CSRF 방어, bearer 방식은 토큰 검증·허용 origin·보관 위험을 검토한다. 허용 origin만 CORS에 등록한다. MFA/재인증은 provider 실제 지원과 연결 상태를 확인해 민감 조치에 적용한다.

## 정보 노출
개인정보는 리스트 마스킹, 원문 DTO 별도, 요청한 필드만 반환. 서버 secret/service role 키는 브라우저·내보내기·로그에 포함하지 않는다.
관리자 서버 접근은 기존 고객 소유권 검사를 대체하지 않는다. DB 서버권한이 RLS를 우회할 수 있으므로 API에서 직원·scope·대상 권한을 항상 확인한다.
공개 schema 새 테이블은 RLS와 실제 grant를 함께 점검한다. 사용자 profile 저장 경로를 일괄 서버권한으로 전환하지 않는다.

## 감사
변경 intent·결과, 민감 원문 reveal, 내보내기 생성·다운로드, 권한 변경, 배포·복구를 기록한다. actorId·대상·사유·requestId·시간·마스킹 diff가 필수.
고위험 변경은 감사/outbox 저장 실패 시 실행하지 않는다. 외부 PG가 이미 성공한 뒤 감사 오류는 거래를 되돌렸다고 가정하지 않고 대사로 복구한다.
break-glass 운영이 필요하면 만료·사유·독립 감사·사후검토를 먼저 설계한다.

## 검증
비직원 API 403, 회수 세션 다음 요청 차단, scope 밖 객체 차단, 자기 승인 차단, 원문 응답 최소화, XSS·SQL 필터 검증, CSV 수식 무력화, 비밀 데이터 로그 차단. 자세한 시나리오는 16 참조.
