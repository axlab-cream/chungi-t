# 운영 런북

## 일일 시작
운영 환경·최종 배포·readiness 확인 → 전일 금융 대사 → 승인 후 미제공 → 생성 실패·PG unknown → 미처리 문의 → 발행 예정 검토.
각 큐에 담당자·다음 확인시각을 남긴다. 장애가 없으면 불필요한 반복 알림을 보내지 않는다.

## 금융 장애
PG 승인 확인은 되는데 주문이 미결제라면: orderId/tid 참조 → 저장된 intent·응답 digest 확인 → PG 상태 대사 → 내부 승인/권한 idempotent 반영 → 고객 경로 재확인.
PG timeout이면: 상태 unknown 유지 → 조회 우선 → 확정 결과 전 재승인/재취소 금지.
차액이면: 기간·타임존·부분환불·test·중복 source_ref를 확인한다. 합계를 맞추려고 주문 금액을 수정하지 않는다.

## 생성 장애
오류코드→storage/model/input/quality/lease 분류. 저장소가 실패하면 재생성부터 하지 않는다. 해당 attempt의 상태·임대·버전을 확인한다.
완료 결과 존재: 재조회. 실패 항목: 한도 내 재시도. 지속 품질 실패: CS에 상태 공유하고 코퍼스·프롬프트 평가 작업 연결.

## 코퍼스·콘텐츠 장애
현재 manifest와 runtime fingerprint 대조 → 직전 승인 release 선정 → 복구 → 신규 합성 요청 snapshot 확인 → 기존 완료 report 불변 확인 → 원인 기록.
고객 결과에 잘못된 내용이 이미 전달된 경우 기존 본문 덮어쓰기보다 별도 안내·정정 정책을 검토한다.

## 출시 체크
후보 빌드/회귀 → 합성 DB·모의 PG → read-only 관리 기능 → 실제 저장소 readiness와 제한 조회 → 기능 플래그별 쓰기 → 고객 로그인·주문목록·UUID 재열람 확인.
운영 배포·실거래는 현재 사용자의 권한 범위 내에서 실행한다. 이 ZIP만으로 운영 실환불·회원삭제를 실행하도록 해석하지 않는다.

## 복구
앱 회귀: 이전 배포 + 관리자 쓰기 플래그 off. 지식 회귀: 이전 manifest. 데이터 회귀: 승인된 백업 복원 계획과 복원 검증. 금융 외부 효과는 DB rollback으로 없어지지 않으므로 대사가 선행한다.
RPO/RTO는 실제 백업·인프라 검증 전 미확정. 초안 목표는 RPO 24h/RTO 4h이나 금전 intent 유실 허용 목표로 사용하지 않는다. 금융 복구는 PG 원장 재대사까지 포함해 목표를 별도 확정한다.

## 주간 운영
문의 원인 상위 항목, 서비스별 제공율, 지식 품질 회귀, 미연결 코퍼스, 비용·지연, 권한 목록·미사용 계정, 보존·export 만료 작업 확인.
담당자 이름·비상연락·배포권한·PG 담당·정책 담당은 프로젝트에서 지정한다.

## 사고 기록 템플릿
발생/탐지/복구 시각, 영향 서비스·건수(확인 범위), 원인 근거, 임시조치, 영구수정, 검증, 미해결, 재발방지 task. 개인정보·비밀값은 넣지 않는다.
