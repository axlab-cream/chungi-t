# PRD: UMSH Operations
제품 책임자: 운영 총괄(지정 필요). 사용자: 운영자, 콘텐츠 편집자, 지식 검수자, CS, 재무, 엔지니어, 분석가.

## 문제
주문·회원·리포트·프롬프트·코퍼스가 서로 다른 코드와 저장소에 분산되어 있다. 관리자가 결제 성공 후 미열람, 생성 실패, 잘못된 카피, 서비스 노출 상태를 한 맥락에서 추적할 운영 제품을 만든다. 모든 화면은 조회에서 근거 확인, 허용된 조치, 결과 검증으로 이어진다.

## 핵심 사용자 시나리오
- CS: 고객의 주문 ID 검색 → 결제 승인과 보고서 상태 확인 → 실패 건을 엔지니어에게 배정 → 복구 후 고객 문의 완료.
- 재무: 일일 대사 차이 조회 → PG 승인 근거 비교 → 중복 결제 확인 → 환불 요청·승인·PG 취소 결과 확인.
- 콘텐츠 담당: 서비스 카드 카피와 포스터 수정 → 실제 랜딩 미리보기 → 검수 → 예약 발행 → 문제 시 직전 버전 복구.
- 지식 담당: 특정 서비스 품질 불만 → 검색된 블록·프롬프트 버전 추적 → 판단 블록 수정 → 평가 → 승인·배포.
- 운영 총괄: 오늘 승인·제공 지연·열린 문의·실패율 확인 → 우선순위 정렬 → 담당자 지정.

## 공통 UX
상단 환경 표시(로컬/스테이징/운영), KST 시간, 전역 검색, 알림. 좌측 고정 업무 내비게이션. 목록은 조밀한 표, 필터 저장, URL 공유, 페이지네이션, 열 선택을 제공한다. 상세는 요약·타임라인·관련 객체·가능 조치를 동일 위치에 둔다. 버튼은 실제 구현한 권한·상태에서만 작동한다.

로딩·빈 결과·필터 결과 없음·부분 실패·권한 없음·연결 끊김을 각각 표현한다. 조회 실패를 매출 0으로 보이지 않게 한다. 변경 실패 시 입력을 유지한다. 충돌 시 서버의 최신 revision과 차이를 보여준다.

## 비기능 목표
관리 조회 API p95 800ms 이하를 10만 합성 주문·20 동시 사용자 조건의 초기 목표로 둔다. 무거운 집계·내보내기·평가·환불은 영속 작업 큐로 분리한다. 키보드 접근·포커스·명시적 라벨·상태 비색상 표시를 검증한다. 모바일은 장애 조회·담당 배정 중심으로 지원하고 복잡한 편집은 폭이 충분한 화면에서 수행한다.

## 출시 조건
M1은 실제 읽기 연결과 권한·마스킹·감사 검증 후 내부 조회용으로 출시 가능하다. M2의 금융 쓰기는 PG 모의 실패·동시성·대사 검증 후 별도 플래그로 연다. M3 발행은 immutable release와 롤백 실습이 선행한다.
