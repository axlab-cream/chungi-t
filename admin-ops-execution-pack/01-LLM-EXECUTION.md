# LLM 실행 지침

## 실행 프롬프트
아래 블록 전체를 구현 에이전트의 첫 요청으로 사용한다.

> 이 패키지를 운명상회 관리자 구현의 작업 명세로 사용하라. 먼저 00, 02, 19를 읽고 연결된 저장소의 WIKI, package.json, src/server/app.ts, 기존 저장소·인증·결제·코퍼스 코드를 대조하라. 패키지의 신규 제안을 이미 구현된 사실로 취급하지 마라. 현재 Git HEAD와 dirty 상태를 기록하고 기존 변경을 보존하라. 15-TASKS의 의존성 순서로 구현하되 초기 목표는 M0와 M1이다. 실제 API, 서버 권한 검증, 영속 저장소에 연결된 관리자 조회 화면을 만들고 목업 데이터만 표시한 상태를 완료로 처리하지 마라. 작업마다 수용 조건과 16-ACCEPTANCE의 관련 검증을 실행하고 20-HANDOFF와 프로젝트 WIKI를 갱신하라. 로컬 구현·테스트를 계속 진행하고, 운영 배포·실제 결제·환불·회원 삭제는 현재 세션에서 별도로 주어진 실행 권한을 확인하라. 권한이 없으면 승인 가능한 구체적 변경·검증 결과까지 준비하라. 기존 고객 리포트, 주소, 소유권, 구매 권한, 완료 본문의 불변성을 유지하라. 환경변수 값과 고객 원문을 출력하거나 커밋하지 마라. 작업이 끝나면 실제 변경 파일, 검증 결과, 남은 기능과 다음 작업 ID를 명시하라.

## 시작 절차
1. 루트의 package.json name과 src/server/app.ts 존재로 원본을 식별한다. 이 ZIP 디렉터리를 앱 루트로 착각하지 않는다.
2. git status --short, git rev-parse HEAD를 기록한다. 원격 운영과 동일하다고 가정하지 않는다.
3. WIKI의 최신 운영 기록과 이 패키지 02를 대조한다. 필요한 최신 외부 API 문서는 구현 단계에서 공식 문서로 확인한다.
4. 기존 관리자 구현이 추가되어 있다면 재사용하고 차이를 ADR로 기록한다.
5. 기존 테스트 기준 결과를 수집한다. npm run typecheck, npm test는 현재 package.json에서 확인된 명령이다. 키가 필요한 통합 검증은 격리된 합성 데이터로 수행한다.
6. 15의 첫 ready 작업을 선택한다. 실행 가능한 의존성이 없다면 원인·해제 조건을 기록한다.

## 구현 규칙
- Express 라우터, TypeScript 서비스·저장소 경계를 우선한다. Next.js 전환이나 신규 인프라 도입은 기본 요구가 아니다.
- 관리자 UI는 실제 API와 연결한다. 초기 빈 데이터는 0, 연결 실패는 오류로 구분한다.
- 권한 검사는 서버에서 한다. 현재 이메일 기반 유료 열람 예외를 운영 관리자 역할로 재사용하지 않는다.
- 신규 스키마는 버전 관리된 마이그레이션과 재실행·복구 계획을 동반한다. 기존 테이블 파괴나 전체 덮어쓰기를 금지한다.
- 외부 부작용 작업은 idempotency, 재시도, 불확정 상태와 대사를 구현한 뒤 활성화한다.
- 새로운 읽기 모델은 구버전 report payload와 누락 필드를 처리해야 한다.
- 파일 코퍼스 편집을 서버리스 로컬 디스크에 저장하는 방식은 운영 CMS가 아니다.
- 도메인별 모듈을 완성하고 검증한다. 문서와 구현 차이는 19에 남긴다.

## 작업 상태
todo → ready → in_progress → review → done. blocked는 이유·담당·해제 조건·다음 비차단 작업을 명시한다. 테스트 실패, 모의 데이터뿐인 API, 임시 인증 우회가 남으면 done 금지.

## 문서 우선순위
현재 사용자의 지시 > 검증된 현재 코드·운영 계약 > 최신 프로젝트 WIKI > 이 패키지의 현황 근거 > 신규 제안. 충돌은 조용히 덮지 말고 19에 기록한다. 실제 운영 기능과 관련된 법적 보존기간·PG 제한은 이 문서를 근거로 확정하지 않는다.
